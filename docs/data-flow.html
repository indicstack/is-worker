is-worker: how the data moves

One frontier model plans and reviews, one dense model on IndicStack writes every ticket, and plain Node scripts sit between them so no model can skip a check. Below: the data-flow diagram, then what each element takes in, does, and puts out, then the factors that never change inside a run.

Frontier model (Claude / Opus) Node scripts Dense model (Qwen on IndicStack) Files on disk dashed = commands or escalation, solid = data

The twelve arrows

  1. Plan to disk. Claude writes BRIEF.md, tickets.jsonl and one test per ticket. Nothing else from Claude touches the project.
  2. Commands. Claude runs doctor, preflight, run, review, table and reads their one-line results. It cannot skip the gate: run calls doctor itself.
  3. Inputs to the worker. The frozen brief (hash checked), the ticket list, the test file for the ticket, the state files (probe window, calibration, settings) and the key from the keychain file.
  4. Request and answer. One streamed chat call per attempt. The answer is classified into exactly one of 12 kinds: ok, length, empty_content, bad_json, runaway, first_token_timeout, stall, total_timeout, http_5xx, network, 429, http_error.
  5. Files to the gate. The parsed files[] go to check.mjs with the ticket and the list of tests already passed.
  6. Verdict back. ok, or the first error (bad path, syntax error, failing test output). The worker turns an error into a one-line fix note and retries once.
  7. Code lands. check.mjs writes only the paths the ticket allows, straight into your project tree (and a copy under outputs/ for the record).
  8. Logs. The scripts append as they go: every call to calls.jsonl; every ticket result to tickets.jsonl; meta.json carries status, calibration used, limiter history, final test count.
  9. Escalation. A ticket that fails twice, overflows the window, or hits a hard error goes to claude-queue.jsonl with the reason; the planner writes it by hand and submits it through the same check.mjs.
  10. Diff for review. make-review builds an isolated folder outside the project with the brief, a unified diff of every file the tickets wrote, and the fixed review prompt; a leak scan refuses if any model, vendor or harness word appears.
  11. Blind review. A headless Opus session with read/write only, no network, no memory of the planning chat, writes REVIEW.md.
  12. Table. Sums from calls.jsonl, the review's token usage and REVIEW.md's verdict become one Markdown row. No number is typed by a model.

Fixed factors

Things that do not change inside a run. A rule change means a new brief version and a new run; a limit change means editing defaults.json and saying so.

The seven rules in every worker call

  1. You are the worker; you write code for exactly one ticket per call.
  2. Output only {"files":[{"path","content"}]}. No prose, no fences.
  3. Write only the files under writes, at those exact paths; return full content for existing files.
  4. The frozen brief is the only specification; follow its rules and interfaces word for word.
  5. Never invent an identifier, path or constant the brief, the existing files or the test do not name.
  6. The shown test runs with node --test against your files; make it pass without changing it.
  7. No new dependencies unless the ticket names them; no comment longer than one line.

Request shape (never varies)

temperature0: same prompt, same answer; retries only when the prompt changed
thinkingoff (chat_template_kwargs.enable_thinking=false)
response_formatstrict JSON schema files_out, no extra keys
streamon, with usage in the final chunk
max_tokensbudget = calibration p95 × 1.5, rounded to 256; first run 2048; doubled once on cut-off
unchanged requestnever resent after a non-transient failure (hash check)

runaway400-char tail repeated 4 times aborts the call
5xxwaits 2 s, 4 s; 3 tries then queue
429waits 15 s, 30 s (or Retry-After); 6 in a row trips the credit breaker, exit 75

test timeout60 s per ticket
concurrencyAIMD: +1 after 2 × limit clean calls, halve on 429/503
spare tokens2,000 kept free in the window
cache-hit filtercalls faster than 1,000 tok/s are server cache hits, excluded from speed stats
